## Архитектурное решение 1. Организация каталога на основе LinkedHashMap для O(1) доступа и предсказуемости порядка (R1, R6)
* **Формулировка решения**: Хранение каталога номенклатурных позиций в агрегате `Warehouse` реализовано через коллекцию `Map<String, StockItem>` (конкретная реализация — `LinkedHashMap`). Коллекция инкапсулирована с модификатором `private final`. Прямые геттеры и сеттеры отсутствуют. Доступ к карточке товара по артикулу осуществляется за константное время $O(1)$. Использование `LinkedHashMap` гарантирует детерминированный порядок итерации элементов (соответствует порядку их первичной регистрации), что важно при формировании отчётов и списков для инвентаризации. Для внешних потребителей методы выборки (`getAllItems`, `findByCategory`) возвращают новые независимые защитные копии списков (`new ArrayList<>(...)`).
* **Рассмотренная альтернатива**: Хранение позиций в виде простого `List<StockItem>` с поиском через цикл for-each за $O(n)$, либо предоставление прямого геттера `getInventory()`, отдающего ссылку на внутреннюю карту.
* **Техническое обоснование**: При увеличении масштаба базы оборудования линейный перебор неизбежно приводит к резкому падению производительности при массовых операциях прихода и отпуска. Структура `Map` обеспечивает мгновенную выборку по хеш-ключу. Защитные копии предотвращают умышленное или случайное повреждение данных внешним кодом (очистка, добавление объектов без валидации).

## Архитектурное решение 2. Локализация контрактной бизнес-логики в сущности StockItem (R2, Fail-Fast)
* **Формулировка решения**: Контроль минимального складского резерва (Вариант 4: не менее 10 шт.) помещён непосредственно в доменную сущность `StockItem`, а именно в метод `decrease(int q)`. При передаче аргумента `q <= 0` или нарушении остатка `quantity - q < 10` немедленно генерируется `IllegalArgumentException` с информативным сообщением, и мутация поля `quantity` не происходит. Класс `Warehouse` в методе `issue` лишь делегирует операцию списания сущности `StockItem`.
* **Рассмотренная альтернатива**: Проверка остатка во внешнем сервисе или контроллере перед вызовом метода уменьшения, либо использование анемичной модели со свободным вызовом `setQuantity(int)`.
* **Техническое обоснование**: Принцип Information Expert (информационный эксперт) требует, чтобы логика, работающая с внутренним состоянием объекта, находилась там, где эти данные хранятся. Инкапсуляция инварианта в `StockItem` гарантирует, что ни один компонент системы не сможет перевести карточку оборудования в некорректное состояние (остаток < 10 или < 0). Стратегия Fail-Fast обеспечивает мгновенное прерывание некорректной операции до фиксации изменений в реестре перемещений `auditLog`.

## Анализ предоставленного фрагмента кода (Антипаттерн)

### Исходный фрагмент:
```java
// Антипаттерн – линейный поиск по List при наличии Map<String,StockItem>
for (StockItem x : items) {              // items – List<StockItem>
    if (x.getCode().equals(code)) {
        return x;                         // O(n) – линейный перебор
    }
}
return null;                              // не найдено
```

### Разбор дефектов и оптимизация:
1. **Выявленные дефекты и неэффективность**: Использование списка `List` и последовательного обхода приводит к вычислительной сложности $O(n)$. Для каждой позиции выполняется вызов `equals()`. При объёме каталога в десятки тысяч позиций и высокой частоте операций прихода/расхода этот участок становится узким местом (bottleneck), нагружая процессор бесполезными итерациями. Возврат `null` провоцирует появление `NullPointerException` в вызывающем коде.
2. **Причина проблемы**: Неудачный выбор структуры данных. Список предназначен для хранения упорядоченных последовательностей, а для задач поиска сущностей по уникальному идентификатору необходима таблица прямого доступа (хэш-таблица).
3. **Корректное решение**: Использование ассоциативного массива `Map<String, StockItem> inventory = new LinkedHashMap<>()`. Поиск выполняется через операцию `inventory.get(code)` за время $O(1)$. Если полученное значение равно `null`, система по правилу R9 сразу выбрасывает `IllegalArgumentException("code not found: " + code)`.
4. **Связь с правилами предметной области**: Исправление напрямую реализует требования правил:
   * **R1**: уникальность кода даёт однозначный ключ в Map;
   * **R6**: сокрытие внутреннего контейнера защищает структуру;
   * **R9**: обязательный контроль присутствия номенклатуры перед проведением операции.

## Ответы на контрольные вопросы к защите работы

### 1. Какая проверка в этой работе защищает программу от наиболее вероятной ошибки входных данных и где она расположена?
Наиболее частой ошибкой при ведении складского каталога является попытка повторной регистрации оборудования с уже занятым артикулом/кодом (например, при повторном вводе накладной или опечатке оператора). Защитой от этого выступает валидация инварианта **R1**, реализованная в методе `addItem(StockItem item)` класса `Warehouse`. Перед вставкой объект проверяется через вызов `inventory.containsKey(item.getCode())`. Если такой код уже зарегистрирован, метод немедленно прерывает выполнение генерацией `IllegalArgumentException`, предотвращая искажение каталога и случайную перезапись существующей номенклатуры.

### 2. Какой метод или класс содержит ключевое бизнес-правило и почему вы разместили его именно там?
Ключевое бизнес-правило — соблюдение неснижаемого технологического запаса оборудования (по Варианту 4: остаток позиции не может стать менее 10 единиц) — реализовано в методе `decrease(int q)` сущности `StockItem`. Оно расположено именно в этом классе в соответствии с принципом High Cohesion и паттерном Information Expert. Сущность `StockItem` является непосредственным владельцем поля `quantity` и обязана самостоятельно отвечать за целостность своего состояния. Это исключает дублирование валидаций и гарантирует соблюдение норматива 10 единиц при любом сценарии списания.

### 3. Как Activity-диаграмма отражает один конкретный участок вашего кода?
Узлы диаграммы «Поиск номенклатуры в карте» и ромб решения «Запись найдена в каталоге склада?» в точности соответствуют логике приватного метода-стража `findExistingItemOrThrow(String code)` в классе `Warehouse`:
```java
StockItem item = inventory.get(code);
if (item == null) {
    throw new IllegalArgumentException("code not found: " + code);
}
```
Если объект не найден (`null`), управление переходит в ветку «Нет» с генерацией исключения `IllegalArgumentException` (правило R9) без создания записи в журнале `auditLog`. Если объект найден, процесс переходит к блоку валидации допустимости операции и проверке резерва 10 единиц.

### 4. Какое изменение требования в этой работе должно затронуть минимальное количество классов и почему?
Корректировка величины неснижаемого запаса (например, изменение порога Варианта 4 с 10 единиц на 20 или 0) затронет исключительно класс `StockItem` — достаточно изменить значение константы `MIN_RESERVE_THRESHOLD`. Ни класс `Warehouse`, ни структура журнала `StockMovement`, ни перечисления не потребуют правок. Это является прямым следствием слабой связности (Low Coupling) архитектуры: агрегат `Warehouse` лишь обращается к контракту метода `decrease`, не вдаваясь в детали численных ограничений.
